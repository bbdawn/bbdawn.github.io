## Pod가 여러 개 생기면 kubernetes가 어떻게 분산시키는지 확인

### Replica를 3개로 변경

- k8s-cp에서

```bash
root@jh-lee2-vm-1:~# kubectl scale deployment nginx --replicas=3
```

```bash
root@jh-lee2-vm-1:~# kubectl get pods -o wide
NAME                     READY   STATUS    RESTARTS   AGE   IP               NODE          NOMINATED NODE   READINESS GATES
nginx-66686b6766-5jww6   1/1     Running   0          50s   192.168.194.66   k8s-worker1   <none>           <none>
nginx-66686b6766-v7plk   1/1     Running   0          51s   192.168.126.4    k8s-worker2   <none>           <none>
```

3개의 Pod가 worker1 2개 + worker2 1개로 배치됨. 

### [test] Pod 1개 삭제 

worker1의 nginx pod 1개를 삭제해도 서비스가 계속 살아있는지 확인

```bash
root@jh-lee2-vm-1:~# kubectl delete pod nginx-66686b6766-5jww6
pod "nginx-66686b6766-5jww6" deleted from default namespace
root@jh-lee2-vm-1:~# kubectl get pods -o wide
NAME                     READY   STATUS    RESTARTS   AGE     IP               NODE          NOMINATED NODE   READINESS GATES
nginx-66686b6766-p9pz5   1/1     Running   0          16s     192.168.194.67   k8s-worker1   <none>           <none>
nginx-66686b6766-v7plk   1/1     Running   0          3m21s   192.168.126.4    k8s-worker2   <none>           <none>
nginx-66686b6766-wvdwf   1/1     Running   0          19m     192.168.194.65   k8s-worker1   <none>           <none>
```

정상적으로 self-healing이 동작함. 

- [기존] nginx-66686b6766-5jww6 —> 삭제됨
- [현재] nginx-66686b6766-p9pz5 —> 새로 생성됨

그리고 Pod가 3개로 유지되고 있음. 

**Pod를 직접 관리하는 것이 아니라 ReplicaSet이 차이를 감지하여 새로운 Pod를 생성해 Deployment가 원하는 상태를 유지함. **

**새 Pod의 IP가 192.168.194.66 → 192.168.194.67로 변경됨. ⇒ Pod가 죽거나 새로 만들어져 IP가 변경되어도 Service가 뒤에서 살아있는 Pod들을 찾아서 연결해줌. **

### 중요 키워드

- [Deployment] replicas : 3 —> nginx pod가 3개 있어야 한다
- [ReplicaSet] 실제로 Pod 3개를 유지한다
- [Pod] 실제 nginx 컨테이너가 실행되는 곳
- [Service] 이 3개의 Pod를 하나의 서비스로 묶어줌 

### [test] pod를 다른 Worker로 옮기는 상황

특정 Worker의 pod를 삭제했을 때 kubernetes가 어떻게 다시 배치하는지 확인 

- worker1 자체에 장애가 발생한 상황 - worker1을 스케줄링 금지 상태로 만들기 

control plane에서 : 

```bash
root@jh-lee2-vm-1:~# kubectl cordon k8s-worker1
node/k8s-worker1 cordoned

root@jh-lee2-vm-1:~# kubectl get nodes
NAME          STATUS                     ROLES           AGE   VERSION
k8s-cp        Ready                      control-plane   47m   v1.34.11
k8s-worker1   Ready,SchedulingDisabled   <none>          45m   v1.34.11
k8s-worker2   Ready                      <none>          45m   v1.34.11
```

cordon : 앞으로 새로운 pod를 이 node에 스케줄링하지 않음. 현재 실행 중인 pod는 그대로 유지 

- worker1에 있는 pod 1개 삭제


worker1에 있는 pod1개를 삭제했더니 새로운 pod가 생성될 때 worker1이 아닌 worker2에 배치됨.

### cordon과 drain의 차이

- cordon : 새 Pod만 못 들어오게 함 
- drain : 기존 Pod까지 다른 Node로 내보냄

```bash
kubectl drain k8s-worker1 --ignore-daemonsets
```

```bash
root@jh-lee2-vm-1:~# kubectl get pods -o wide
NAME                     READY   STATUS    RESTARTS   AGE     IP              NODE          NOMINATED NODE   READINESS GATES
nginx-66686b6766-hrcjd   1/1     Running   0          70s     192.168.126.6   k8s-worker2   <none>           <none>
nginx-66686b6766-px4jk   1/1     Running   0          7m13s   192.168.126.5   k8s-worker2   <none>           <none>
nginx-66686b6766-v7plk   1/1     Running   0          27m     192.168.126.4   k8s-worker2   <none>           <none>
```

**worker1의 기존 nginx Pod까지 worker2로 이동**

**→ Pod가 worker1에서 worker2로 이동한 것은 정확히 말하면, 기존 pod가 이동한 것이 아님. 기존 pod가 삭제되고, replicaset이 새로운 pod를 만든 것. 그래서 pod이름도 바뀌고 ip도 바뀌며 service가 이 변화를 자동으로 반영한 것. **
